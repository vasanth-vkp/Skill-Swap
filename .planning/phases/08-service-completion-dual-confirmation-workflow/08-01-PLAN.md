# Plan 08-01: Dual-Confirmation Completion State Machine, Dispute Handling Endpoints & Frontend Verification

## Objective
Implement the complete dual-confirmation service completion and dispute handling workflow:
- Backend: Extend `ExchangeRequest` with independent provider/requester completion flags, timestamps, and dispute tracking. Implement completion confirmation logic that automatically transitions status to `COMPLETED` when both participants confirm, and dispute logic that flags the exchange as `DISPUTED`.
- Frontend: Enhance `ExchangeCard` with interactive dual confirmation progress badges, highlight reciprocal verification prompts, build `DisputeExchangeModal` for filing structured disputes, and wire up `exchangeService.js`.

## Execution Context
- Spring Boot 3.3.4, Java 21, Spring Data JPA, Spring Security JWT
- React 19, Vite, Tailwind CSS, Lucide Icons, Vitest + React Testing Library
- Existing components: `ExchangeRequest.java`, `ExchangeService.java`, `ExchangeController.java`, `ExchangeCard.jsx`, `Exchanges.jsx`, `exchangeService.js`

    4. Update ExchangeDto.java:
       - Add fields: `providerConfirmed`, `requesterConfirmed`, `providerConfirmedAt`, `requesterConfirmedAt`, `disputeReason`, `disputedById`, `disputedAt`.
       - Map these fields in `fromEntity(ExchangeRequest request)`.
    5. Update ExchangeService.java:
       - Add `confirmCompletion(Long exchangeId, Long userId)`:
         - Verifies exchange exists; caller is either requester or provider (otherwise throws `SecurityException` -> 403).
         - Checks exchange status is `SCHEDULED` or `ACCEPTED` (otherwise throws `IllegalStateException` -> 400).
         - If caller is provider, set `providerConfirmed = true`, `providerConfirmedAt = Instant.now()`.
         - If caller is requester, set `requesterConfirmed = true`, `requesterConfirmedAt = Instant.now()`.
         - If both `providerConfirmed && requesterConfirmed`:
           - Set `status = ExchangeStatus.COMPLETED`.
           - Find any active `Booking` for this exchange in `SCHEDULED` status and set its status to `BookingStatus.COMPLETED`.
         - Save and return `ExchangeDto.fromEntity(request)`.
       - Add `disputeExchange(Long exchangeId, Long userId, String reason)`:
         - Verifies exchange exists; caller is either requester or provider (otherwise throws `SecurityException` -> 403).
         - Checks exchange status is not already `COMPLETED`, `CANCELLED`, or `REJECTED` (otherwise throws `IllegalStateException` -> 400).
         - Set `status = ExchangeStatus.DISPUTED`, `disputeReason = reason`, `disputedBy = user`, `disputedAt = Instant.now()`.
         - Save and return `ExchangeDto.fromEntity(request)`.
    6. Update ExchangeController.java:
       - Add endpoint `POST /api/v1/exchanges/{id}/complete`:
         - Calls `exchangeService.confirmCompletion(id, currentUser.getId())`.
         - Returns 200 OK with `ExchangeDto`.
       - Add endpoint `POST /api/v1/exchanges/{id}/dispute`:
         - Accepts `@Valid @RequestBody DisputeRequest disputeRequest`.
         - Calls `exchangeService.disputeExchange(id, currentUser.getId(), disputeRequest.getReason())`.
         - Returns 200 OK with `ExchangeDto`.
    7. Update tests in ExchangeServiceTest.java & ExchangeControllerTest.java:
       - Test: Provider confirming sets `providerConfirmed=true` but keeps status `SCHEDULED`.
       - Test: Requester confirming second transitions status to `COMPLETED` and marks booking `COMPLETED`.
       - Test: Non-participant confirmation throws 403 Forbidden.
       - Test: Confirming an already completed or cancelled exchange throws 400 Bad Request.
       - Test: Disputing an exchange transitions status to `DISPUTED` and records reason.
       - Test: Disputing with blank reason returns 400 Bad Request.
       - Test: Non-participant disputing returns 403 Forbidden.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> ExchangeController /complete | Authenticated caller triggers their side of completion confirmation |
| Client -> ExchangeController /dispute | Authenticated caller files structured dispute reason |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-01 | Tampering | ExchangeService | high | mitigate | Verify authenticated caller is participant; non-participants receive 403 Forbidden |
| T-08-02 | Tampering | ExchangeService | high | mitigate | Disallow completing/disputing already completed, cancelled, or rejected exchanges |
| T-08-03 | Spoofing | DisputeExchangeModal | med | mitigate | Server enforces authenticated user session and records caller ID as `disputedBy` |
| T-08-04 | Repudiation | ExchangeRequest | med | mitigate | Independent timestamps stored for provider and requester confirmations |
| T-08-05 | Denial of Service | ExchangeCard | low | mitigate | Loading states prevent duplicate click submissions; idempotent completion handling |
</threat_model>
