# Plan 11-01: Backend Notification Entity, Lifecycle Triggers, REST API & Security

## Objective
Build the server-side in-app notification infrastructure for SkillSwap:
- Define `Notification` entity and `NotificationType` enum matching the Flyway `notifications` schema.
- Implement `NotificationRepository` with indexed queries (`findByUserIdOrderByCreatedAtDesc`, `countByUserIdAndIsReadFalse`, `markAllAsReadByUserId`).
- Create `NotificationService` that handles notification persistence, unread counting, marking single/all as read, and domain event dispatch.
- Wire notification generation into key exchange lifecycle operations:
  - Exchange request created (`REQUEST_RECEIVED` -> provider)
  - Exchange request accepted (`REQUEST_ACCEPTED` -> requester)
  - Exchange request rejected (`REQUEST_DECLINED` -> requester)
  - Booking scheduled (`BOOKING_SCHEDULED` -> counterparty)
  - Service completed / credit transferred (`SERVICE_COMPLETED` / `CREDIT_TRANSFERRED` -> both parties)
  - Review submitted (`REVIEW_RECEIVED` -> reviewee)
- Expose authenticated REST endpoints via `NotificationController`:
  - `GET /api/v1/notifications`: List current user's notifications.
  - `GET /api/v1/notifications/unread-count`: Returns `{ unreadCount: number }`.
  - `PATCH /api/v1/notifications/{id}/read`: Marks notification as read.
  - `PATCH /api/v1/notifications/read-all`: Marks all notifications as read for current user.
- Write unit and integration tests (`NotificationServiceTest`, `NotificationControllerTest`).

## Execution Context
- Spring Boot 3.3.4, Java 21, Spring Data JPA, Spring Security with JWT.
- Existing services: `ExchangeService`, `BookingService`, `WalletService`, `ReviewService`.
- Existing entity: `User`, `Notification` table in Flyway V1.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> NotificationController | Authenticated user queries and updates only their notifications |
| Service -> NotificationService | Internal system calls create notifications based on verified business transactions |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-01 | Tampering | NotificationService | high | mitigate | Notifications are triggered strictly by backend services; no direct public notification creation endpoint |
| T-11-02 | Information Disclosure | NotificationController | high | mitigate | User principal injected via Spring Security; repository queries explicitly filtered by `userId` |
| T-11-03 | Elevation of Privilege | NotificationController | med | mitigate | Marking a notification as read validates `notification.user.id == principal.id` |
</threat_model>
