# Plan 07-01: Backend Booking Domain, Scheduling, Conflict Detection & REST API

## Objective
Implement the backend booking and scheduling domain enabling accepted exchange participants to schedule sessions with automatic duration calculation, prevent calendar conflicts across participants, reschedule upcoming sessions, and cancel bookings with automatic exchange status reversion to `ACCEPTED`.

## Execution Context
- Spring Boot 3.3.4, Java 21, Spring Data JPA, Spring Security JWT
- Database table `bookings` already created in `V1__init_schema.sql`
- Linked entity `ExchangeRequest` from Phase 6

<task type="auto">
  <name>Task 2: BookingService with Conflict Detection & Unit Tests</name>
  <files>
    backend/src/main/java/com/skillswap/platform/booking/service/BookingService.java,

  <action>
    1. Implement BookingService.java (@Service, @Transactional):
       - `scheduleBooking(Long exchangeId, ScheduleBookingRequest request, Long currentUserId)`:
         - Lookup ExchangeRequest. Ensure exchange exists.
         - Participant check: currentUserId must equal requester.id or provider.id.
         - Status check: exchange.status must be `ACCEPTED` or `SCHEDULED`.
         - Timing check: `startTime` must be at least 15 minutes in the future from `Instant.now()`.
         - Compute `endTime = startTime.plus((long)(exchange.getDuration().doubleValue() * 60), ChronoUnit.MINUTES)`.
         - Conflict check: call `findOverlappingBookings` for both requester and provider. If either has overlapping active booking, throw `IllegalStateException` ("Calendar conflict detected...").
         - If existing active booking exists for this exchange, cancel or update it; otherwise create new `Booking`.
         - Update `exchange.setStatus(ExchangeStatus.SCHEDULED)`.
         - Return `BookingDto.fromEntity(savedBooking)`.
       - `rescheduleBooking(Long bookingId, ScheduleBookingRequest request, Long currentUserId)`:
         - Lookup Booking. Participant check (currentUserId is requester or provider).
         - Status check: booking must be `SCHEDULED`.
         - Timing check: `startTime` >= now + 15 min.
         - Compute `endTime = startTime + (duration * 60 min)`.
         - Conflict check excluding current booking ID (`excludeBookingId = booking.getId()`).
         - Update `startTime` and `endTime`. Return updated `BookingDto`.
       - `cancelBooking(Long bookingId, Long currentUserId)`:
         - Lookup Booking. Participant check.
         - Set `booking.setStatus(BookingStatus.CANCELLED)`.
         - Set `exchangeRequest.setStatus(ExchangeStatus.ACCEPTED)` (D-702).
         - Return `BookingDto`.
       - `getUpcomingBookings(Long currentUserId)`:
         - Call `findUpcomingBookings(currentUserId, BookingStatus.SCHEDULED, Instant.now())`.
         - Map to list of `BookingDto`.
       - `getBookingForExchange(Long exchangeId, Long currentUserId)`:
         - Validate participant. Return active booking or empty.
    2. Write BookingServiceTest.java:
       - Test successful booking creation with automatic duration computation.
       - Test rejection when caller is not an exchange participant (SecurityException).
       - Test rejection when exchange is not in ACCEPTED or SCHEDULED status (IllegalStateException).
       - Test rejection when startTime is in the past or < 15 minutes away (IllegalArgumentException).
       - Test rejection when requester or provider has an overlapping active booking (IllegalStateException).
       - Test successful rescheduling with updated start and end times.
       - Test cancelling booking updates status to CANCELLED and resets exchange status to ACCEPTED.
       - Test getUpcomingBookings returns chronological list for participant.
